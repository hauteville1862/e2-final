## 2. 작업 방식 (합의된 규칙)

1. **코드는 사용자가 직접 작성한다.** 미션.md의 요구사항 순서대로 사용자가 코드를 붙여넣으면, 검토·테스트하고 커밋한다. 사용자가 명시적으로 요청할 때만 코드를 대신 수정한다.
2. **커밋 전 승인을 받는다.** 커밋 메시지와 대상 파일을 구분선으로 분리한 **별도 블록**으로 제시하고, 승인 후에만 `git commit` / `git push`를 실행한다. 긴 설명 끝에 한 줄로 끼워 넣지 않는다.
3. **질문은 한 번에 하나씩** 제시한다.
4. **커밋 메시지 접두사는 6종만** 사용한다 — `Feat` / `Fix` / `Docs` / `Refactor` / `Chore` / `Test`. 본문은 한국어로 작업 내용이 드러나게 쓴다. (미션.md:275 근거, 평가 2-5 대응)
5. **`docs/작업기록.md`는 하루 작업이 끝날 때만** 별도 `Docs:` 커밋으로 올린다. 기능 커밋에 섞지 않는다.

### 5-2. 환경 관련 주의사항 (반복해서 겪은 문제)

**push는 PowerShell에서 해야 한다.** WSL에는 GitHub 자격 증명이 없어 인증 실패한다. GitHub는 비밀번호 인증을 지원하지 않으므로, WSL에서 하려면 토큰이나 SSH 키를 따로 설정해야 한다. 커밋·브랜치 작업은 WSL에서 해도 문제없다.

**WSL에서 `git checkout`이 실패하는 문제.** Windows Git은 `core.autocrlf=true`라 작업 폴더 파일이 CRLF 줄바꿈이다. WSL Git에는 그 설정이 없어 모든 파일을 "수정됨"으로 인식한다. 해결하려면 WSL에서 `git config --global core.autocrlf input`. 또는 그냥 PowerShell을 쓴다.

**`git log`가 반복 출력되는 것처럼 보이는 현상**은 페이저(`less`) 때문이다. `q`로 빠져나온다. 스크린샷을 찍을 때는 `git --no-pager log --oneline --graph`.

**VS Code에 파일을 열어둔 채 편집하면 덮어써질 수 있다.** 실제로 `storage.py` 수정분이 편집기 버퍼에 밀려 되돌아간 적이 있다. 파일을 고치기 전에는 해당 탭을 닫거나 저장 상태를 확인할 것.

### 5-3. 브랜치

- `main` — 기본 브랜치
- `feature/quiz_game` — 6단계 작업용. 병합 완료. **삭제하지 말 것** (평가 1-6 확인 자료)

병합은 `git checkout main` 후 `git merge feature/quiz_game --no-edit`. `--no-edit`은 편집기(vim)가 열리는 것을 막는다.

### 5-4. 커밋을 단계별로 나누는 방법

한 파일에 여러 단계 분량이 들어와 있을 때, 해당 단계 부분만 남기고 나머지를 잠시 덜어낸 뒤 커밋하고 곧바로 복원했다. 덜어낸 코드는 스크래치패드에 백업했다. `storage.py`를 5단계(기본 데이터)와 11단계(load/save)로 나눌 때 사용.

## 7. 설명 준비 (평가 대비)

### 7-1. 클래스를 4개로 나눈 이유 (평가 2-1) — 미션 예시와 다른 점

미션.md:176–181은 `QuizGame` 하나가 메뉴·퀴즈 풀기·추가·목록·점수·파일 입출력을 모두 담당하는 그림을 제시한다. 이 프로젝트는 네 클래스로 나눴다(3절 표 참고).

**설명 논리**: 미션은 "최소 2개 이상의 클래스로 역할을 분리"(269행)를 요구하고, 그 기준을 넘겨 4개로 나눴다. 나눈 기준은 **"무엇이 바뀔 때 이 파일을 고치게 되는가"**다.

**예상 질문**: "미션은 `QuizGame`이 전부 관리한다고 했는데요?"
→ "미션의 `QuizGame`은 최소 구성 예시로 이해했습니다. 게임 진행 상태(`QuizGame`)와 사용자 입출력(`QuizCLI`)을 나누는 편이 각각을 설명하기 쉬웠습니다. `QuizGame`은 '한 판의 진행'을 맡는다고 정의했습니다."

### 7-2. 클래스를 쓴 이유 (평가 3-1)

핵심 문장: **"문제에 관한 일은 문제 자신이 한다."**

리팩터링 전에는 `quiz_cli.py`가 `current_quiz.question`, `.choices`를 직접 꺼내 출력했고, `quiz_game.py`가 `.answer`를 직접 비교했다. 지금은 `Quiz.show(번호)`와 `Quiz.is_correct(답)`을 호출한다. 바깥에서는 내부 구조를 몰라도 된다.

함수만으로 만들었다면 `show_quiz(question, choices)`처럼 매번 데이터를 넘겨야 하고, 문제가 여러 개일 때 지문·선택지·정답의 짝이 어긋나지 않도록 따로 관리해야 한다.

### 7-3. 메서드를 나눈 기준 (평가 2-2)

`run_quiz`는 처음에 60줄이었다. 불러오기, 객체 변환, 문제 진행, 중단 처리, 결과 저장을 한 곳에서 했다. "이 함수가 무엇을 하나"에 한 문장으로 답할 수 없어 `create_quiz_list` / `ask_one_quiz` / `save_result`로 분리했다.

분리 후 핵심은 두 줄로 읽힌다.
```python
while game.still_has_quizzes():
    self.ask_one_quiz(game)
```

입력 검증도 두 함수로 정리했다. `get_valid_int`는 숫자 검사(메뉴·정답·정답 번호에서 재사용), `get_nonempty_text`는 빈 문자열 검사(문제 지문·보기).

### 7-4. 예외를 진입점에서 잡은 이유 (평가 2-4)

`Ctrl+C`는 프로그램 어디서든 발생할 수 있다. `input()`마다 처리를 넣으면 같은 코드가 흩어진다. 파이썬은 예외를 처리하는 곳을 만날 때까지 호출한 함수를 거슬러 올라가므로, 진입점에서 한 번 잡으면 어디서 발생하든 그곳으로 온다.

퀴즈 도중 중단 시에는 `run_quiz`가 먼저 기록을 저장하고 인자 없는 `raise`로 같은 예외를 다시 던진다. **저장은 데이터를 아는 곳에서, 종료 안내는 진입점에서.**

`except Exception`으로 전부 잡지 않은 이유: 오타로 인한 `NameError` 같은 진짜 버그까지 삼켜서 문제를 발견하지 못하게 된다.

`sys.exit(0)`의 0은 정상 종료를 뜻하는 종료 코드. 의도한 대로 처리하고 끝냈으므로 오류가 아니다.

### 7-5. 부모 클래스 하나로 여러 예외 잡기 (평가 3-3)

- `load()`의 `except OSError` — `FileNotFoundError`(첫 실행), `PermissionError`(열 수 없음)가 모두 하위 클래스
- `load()`의 `except ValueError` — `json.JSONDecodeError`가 하위 클래스. 키 누락과 딕셔너리 아님은 직접 `raise ValueError`로 같은 경로에 합류
- `save()`의 `except OSError` — 권한 없음, 디스크 가득 참 등

**두 갈래로 나눈 이유**: 파일에 **접근할 수 없는 것**은 사용자 잘못이 아니고 첫 실행도 여기 해당하므로 조용히 기본 데이터를 쓴다. **내용이 잘못된 것**은 저장된 데이터가 사라지는 상황이므로 반드시 알린다.

### 7-6. state.json 구조 설계 (평가 3-5, 4-2)

`play_count`를 둔 이유: 초기에는 `best_score`만 저장했는데, 5문제를 모두 틀려 0점을 받은 뒤 점수를 확인하니 "아직 풀지 않았다"고 표시됐다. 숫자 하나에 "최고 점수가 몇 점인가"와 "플레이한 적이 있는가" 두 의미를 담으려 한 것이 원인.

**필드 추가와 이름 변경의 차이**(평가 4-3에서 쓸 수 있음):
- 필드 **추가**(`play_count`)는 `if "play_count" not in data` 한 줄로 옛 파일을 그대로 살릴 수 있다
- 필드 **이름 변경**(`high_score`→`best_score`, `questions`→`quizzes`)은 옛 이름을 새 이름으로 옮기는 변환 코드가 따로 필요하다. 이번에는 변환 코드를 넣지 않아, 옛 형식 파일은 손상으로 판정되어 초기화된다

### 7-7. 브랜치와 병합 (평가 3-4)

`feature/quiz_game`에서 6단계를 작업하는 동안 `main`에는 문서 커밋이 따로 쌓였다. 병합 커밋은 **부모가 둘**이다(`65cea0e`와 `c216597`). 그래서 그래프에 다이아몬드 모양이 생긴다.

스크린샷 `git_log_graph_before_merge.png`(갈라짐)와 `git_log_graph_after_merge.png`(합쳐짐)를 나란히 보여주면 된다.

### 7-8. 채점 순서가 중요한 이유 (평가 1-2)

`QuizGame.submit_answer`는 정답 판정을 **먼저 하고** `quiz_number`를 증가시킨다. 순서가 반대면 다음 문제의 정답과 비교하게 되어 채점이 전부 틀어진다.

### 7-9. 준비해둘 만한 추가 답변

**"퀴즈가 1000개로 늘어나면?" (평가 4-1)**
현재는 실행할 때마다 파일 전체를 읽고, 저장할 때도 전체를 다시 쓴다. 퀴즈 하나를 추가하려고 1000개를 통째로 다시 쓰는 셈이라 느려진다. 메모리에도 전부 올라간다. 또 저장 도중 프로그램이 중단되면 파일 전체가 깨질 수 있다. 개선하려면 데이터베이스(SQLite 등)를 쓰거나, 임시 파일에 쓴 뒤 교체하는 방식을 쓴다.

**"채점 방식이 바뀌면 어디를 고치나?" (평가 4-3)**
- 정답 판정 규칙 → `Quiz.is_correct()`
- 점수 계산(예: 백분율) → `QuizGame.submit_answer`, `save_result`
- 선택지 개수 → `Quiz`(출력), `get_valid_int` 호출부의 범위 인자, `add_new_quiz`의 `range(1, 5)`

**"0점과 미기록을 어떻게 구분하나?"**
`play_count` 필드. 7-6 참고.

## 8. 검증 방법

입력을 미리 넣어 자동 확인할 수 있다. 한글이 깨지면 `PYTHONIOENCODING=utf-8`을 앞에 붙인다.

```bash
# 퀴즈 풀기 (정답 5개 → 엔터 → 종료)
printf '1\n1\n2\n2\n4\n1\n\n5\n' | python main.py

# 잘못된 입력 처리
printf ' 1 \nabc\n9\n\n5\n' | python main.py

# EOF 안전 종료
python main.py < /dev/null

# 퀴즈 도중 중단 시 저장 확인 (2문제만 풀고 EOF)
printf '1\n1\n2\n' | python main.py

# 손상 파일 복구
echo '{broken' > state.json && python main.py

# 딕셔너리가 아닌 JSON
echo '5' > state.json && python main.py

# 퀴즈가 없는 경우
echo '{"best_score": 0, "play_count": 0, "quizzes": []}' > state.json && python main.py
```

**주의**: 테스트하면 `state.json`이 바뀐다. 커밋 전에 기본 상태로 되돌릴 것.

```bash
rm -f state.json && python -c "from storage import Storage; s=Storage(); s.save(s.get_default_data())"
```
